# Plugin development requirements

Read this page only when developing, modifying, or reviewing plugin commands.

These requirements apply before following the procedures below.

- Implement the feature and make the normal use flow work first. Then review whether security measures and restrictions are necessary.
- Do not let additional restrictions or development checks block feature implementation.
- A command must perform the operation it promises, and the plugin itself must check the result.
- Do not turn development notes, test steps, or acceptance procedures into prerequisites for ordinary use.
- Do not add unnecessary restrictions for development convenience, historical issues, or host behavior differences.
- When host behavior differs, improve the plugin's adaptation; do not use new restrictions as a substitute for a fix.
- Checks that the plugin can perform must be performed inside the plugin, not delegated to the user.
- Keep only checks necessary to prevent editing the wrong project, using the wrong connection, duplicate writes, or clear runtime errors.
- For every new restriction, explain the specific error it prevents and prefer handling it internally in the plugin.
- When the result can be confirmed, explicitly return success or failure; do not always return “pending verification.”
- When the result truly cannot be confirmed, explain why and stop operations that depend on it. Do not automatically retry a write with an unknown result.
- Before delivery, verify that the normal use flow completes; a successful compile alone is not sufficient.

## Handling source records inside the plugin

This section is for internal plugin implementation only. Do not edit document source directly during ordinary drawing.

- Document source is a **line-oriented JSON change log** (`JSON(header)||JSON(data)`). For a given `(type,id)`, `ticket` determines which record is newer; an empty `data` body is a deletion tombstone. It is not a snapshot.
- Safe writes are **append-only**: (1) do not edit old lines; append changes to the end.
- (2) Assign monotonically increasing tickets starting at `max + 1`.
- (3) To modify a primitive, shallow-copy its original `data` and overwrite only the keys being changed.
- (4) When moving a component, update both coordinate sets together: `x/y/angle` and `positionX/positionY/rotation`.
- (5) Delete with a tombstone; do not physically remove a line.
- (6) Back up the entire source before writing. Read back and compare each value afterward (tolerance 0.001); restore the whole source on failure; call save only after every check passes.
- Give all generated primitives the `spg_` prefix and document-layer `layerId=13` so they can be cleaned up.
- The pipeline is wrapped by `pcb.groupBySchematicRegions` and `pcb.sourceRollback` (infrastructure: `src/pcb/sourcelog.ts`).
