# Plugin development requirements

Read this page only when developing, modifying, or reviewing plugin commands.

Follow these requirements before the workflow below:

- Implement the feature and make the normal usage flow work before reviewing security and limitations.
- Do not let extra restrictions or development checks block feature implementation.
- A command must do what it promises and the plugin must check the result itself.
- Do not make development notes, test steps, or acceptance procedures prerequisites for ordinary use.
- Do not add useless restrictions for developer convenience, historical issues, or host differences.
- Adapt the plugin to host differences; do not use extra restrictions as a substitute for fixing them.
- Perform checks inside the plugin when the plugin can do them; do not shift them to the user.
- Keep only checks needed to prevent modifying the wrong project, using the wrong connection, duplicate writes, or clear runtime errors.
- For every new restriction, state the specific error it prevents and first consider handling it inside the plugin.
- When the result is knowable, explicitly return success or failure; do not always return “needs verification.”
- When the result truly cannot be confirmed, explain why and stop operations that depend on it. Do not automatically retry a write with an unknown result.
- Before delivery, check that the normal usage flow completes; compilation alone is not sufficient.

## Handling source records inside the plugin

For plugin implementation only. Ordinary drawing must not write document source directly.

- Document source is a **line-oriented JSON change log** (`JSON(header)||JSON(data)`); records sharing `(type,id)` are ordered by ticket, and empty data is a deletion tombstone. It is not a snapshot.
- Safe writes are **append-only**: (1) do not edit old lines; append changes at the end. (2) Use monotonically increasing tickets starting at `max+1`. (3) Modify a primitive by shallow-copying its original data and overriding only the required keys. (4) When moving a component, update both coordinate fields (`x/y/angle` and `positionX/positionY/rotation`). (5) Delete with a tombstone, never by physically removing a line. (6) Back up the entire source before writing; read it back and compare each value (tolerance 0.001). On failure, restore the full source. Save only if all checks pass.
- Give generated primitives the `spg_` prefix and document layer `layerId=13` so they can be cleaned up.
- The pipeline is wrapped by `pcb.groupBySchematicRegions` and `pcb.sourceRollback`; infrastructure is in `src/pcb/sourcelog.ts`.
